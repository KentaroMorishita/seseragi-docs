# 公式ドキュメントの構成

対象版は`src/data/standard-library.json`の`languageVersion`で管理し、ページ上部の共通表示にだけ出す。本文・APIの表・検索内容に版番号を繰り返さない。日本語を標準とし、同じ章・例・条件を英語でも提供する。

## 読者と入口

JavaScriptやTypeScriptの経験があり、Seseragiでプログラムを書きたい読者を主な対象とする。関数型プログラミングの用語を前提にせず、まず動く例から値・関数・型・Effectを説明する。

| 場所 | 読者の目的 | 掲載する内容 |
| --- | --- | --- |
| 概要 | Seseragiの考え方と入口を知る | 言語の特徴、TypeScriptとの違い、読む場所の選択 |
| 学ぶ | 順に理解してコードを書く | 値と式から型、合成、Effect、Signal、moduleへ進む教材 |
| 用途別ガイド | 具体的なアプリを作る | CLI、Web、状態とAction、フォーム、テスト、外部連携、公開 |
| 言語リファレンス | 正確な規則を確認する | 構文、型、評価、制約、失敗、module、tooling、実行境界 |
| 標準ライブラリ | APIを選び、型を確認する | moduleの用途、対象環境、公開型と関数、制約、関連教材 |

Playgroundは実験の場として共通ナビゲーションから開く。仕様や開発手順の説明をGitHubのMarkdownファイルへ委ねない。リポジトリのソースとリリースのダウンロードにはリンクできる。

## 学ぶ順番

1. 一行の文字列表示から始める最初のプログラムとローカル環境
2. 値と式、関数とパイプライン
3. recordとstruct、代数的データ型、パターンマッチ
4. ArrayとList、MaybeとEither
5. genericと再帰
6. EffectとSignal
7. 型クラスとmodule

章の区切りと順番は日英の`meta.json`に明記する。各教材は前提・動く例・意味の説明・試す課題・次に読む場所を持つ。最初の例は、その節が教える一つの概念に絞る。呼び出しと式のグループ化、文字列表示とADTなどを、説明前に一つの作例へ混ぜない。トップのコードは言語の特徴を示す例とし、すべての教材に使い回さない。リファレンスは教材の繰り返しではなく、規則と境界を調べられるようにする。

一つの章に置く例の数は制限しない。まず短い基本形を示し、入力の違い、空・該当なし・失敗、操作の使い分けを、必要な箇所で読み比べられるようにする。それぞれの例に、何を見るかと入力・結果の対応を添える。習った概念を組み合わせる例は、その後に置く。

短い式や定義を見せるために、毎回アプリ全体を再掲する必要はない。宣言、式、`main`の中へ置く断片、独立して実行できるファイルの違いを本文で明示する。断片も検証用プログラムから抽出し、掲載内容と実行結果を照合する。標準ライブラリでは、処理対象や結果が異なるAPIの使い分けを、目的別の小さな例で示す。

## 正確さと更新

- 言語の意味はSeseragiリポジトリの`docs/spec`、現行動作はリリース済みCLIと実行fixtureで照合する。
- 仕様にある将来の契約と、今使えるAPIを区別する。古い進捗表を実装済み判定には使わない。
- 標準ライブラリの型と公開名はコンパイラの公開型情報から取得する。説明は日英で管理し、更新時に欠落を検査する。
- 実行例は掲載本文と検証ファイルを照合し、出力または期待する診断を確認する。Webのビルド成功とブラウザ上の操作確認は別々に記録する。
- ページの言語対応、内部リンク、見出しアンカー、検索、スマホ表示、コードコピーを検査してから公開する。

## 表示

承認済みの配色・余白・トップページの方向を使う。見出しやブランドに負の字間を設定しない。短い関数シグネチャを不自然に分割せず、長い式は構文の区切りで改行する。パイプラインは初期値と各`|>`を同じ字下げで縦に並べる。

## 読者レビュー

エージェントによる構成・仕様レビューと、実際の初見読者による評価を分けて記録する。公開後も、型と分岐を説明できるか、コードを変えて動かせるか、必要なAPIを探せるかを読者に確かめ、つまずいたページを改める。
