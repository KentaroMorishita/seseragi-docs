# Seseragi Docs

- This repository owns the Astro + Fumadocs website. The compiler, Playground, and normative language specification live in `KentaroMorishita/seseragi`.
- Display pipelines vertically: place each `|>` stage on its own line, aligned at the same indentation as the initial value.
- Showcase code must express idiomatic Seseragi: meaningful types, pattern matching, and composition. Do not add top-level bindings just to name fixed inputs, or split a short signature between its name and parameters. Keep signatures together, break the body expression where useful, and verify authored lines fit phone screens before relying on CSS wrapping.
- Do not apply negative letter-spacing to headings, navigation, or the brand. Use normal tracking and solve width constraints with layout or intentional line breaks.
- Reader-facing documentation must stay on this website. Do not link to GitHub Markdown/spec/status/getting-started files as a substitute for explanations. Repository source links and release downloads may remain.
- Keep Learn (guided explanations) and Reference (lookup) separate. Validate the information architecture and visible design before expanding content broadly.
- Author Japanese prose in `content/docs`. Use concrete examples that compile with the canonical Seseragi CLI. Record the tested compiler version.
- The syntax grammar and brand assets are copied from the language repository; record provenance when updating them.
- Use Node 24.22.1 and Bun 1.4.4. Run `bun run check` and `bun run build` for site changes. Verify navigation, search, mobile layout, and hydration in a browser when UI changes.
- Preserve unrelated work. Never commit `.env*`, `.vercel`, generated `dist`, browser state, or tokens.
- This is the official documentation site. Maintain a complete learning path, task guides, exact language reference, and compiler-derived library reference. Do not publish placeholder pages. Automated checks and agent reviews are not real-reader acceptance.
- Every page needs a full Japanese and English counterpart at the same relative path. Keep chapter order explicit in `meta.json`; keep explanations, task instructions, and exact contracts in their owning section.
- Executable examples must be verified against the documented CLI version. Keep displayed code synchronized with the checked source through `{/* example: examples/... */}` markers. Distinguish signature fragments, expected errors, browser builds, and executed programs.
- Update library snapshots only through `scripts/sync-library.mjs`. Never present contract-only modules or future CLI/specification proposals as released functionality.
- Keep teaching examples focused on one concept at a time. The first program prints one string; introduce function calls, grouping, ADTs, effects, and composition in their own steps. A homepage showcase is not a universal tutorial example.
- Supply several small examples when inputs, absence, failure, or a choice of operations change the lesson. Show the input, relevant code, and observable result together; do not enforce one sample per chapter or expand every fragment into a full app. Named excerpts use `// docs:start name` and `// docs:end name` in checked source, referenced as `{/* example: examples/path.ssrg#name */}`. Clearly label expressions, declarations, and excerpts used inside `main`.
- The documented release comes from `src/data/standard-library.json` and is displayed only by the common article header. Do not put release numbers or version components in article bodies, generated API tables, or search content. Package versions inside executable code examples and dated internal verification records retain their own meaning. Generated library pages are maintained by their renderer. On upgrades, review release-specific claims and signature corrections, then run `bun run verify:release -- --reviewed` and the site/browser checks. Never hand-edit `release-verification.json` or relabel unverified examples as checked on a new release. See README.md for the update sequence.
