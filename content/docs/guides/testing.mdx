---
title: テストを書く
description: 公開APIをstd/testで検証し、境界値を継続して確かめる。
---

小計3000以上なら送料0、それより小さければ400になる関数をテストします。境界の直前、境界そのもの、境界の直後を固定し、変更で条件をずらしていないか確認します。

[関数とパイプライン](/docs/learn/functions-and-pipelines)、[モジュール](/docs/learn/modules)、[Effect](/docs/learn/effects)の構文を使います。テストのファイル構成とrunnerの操作は、以下で準備します。

## テスト用のパッケージを作る

`shipping/`に次の構成を作ります。CLIとBunが必要です。テストは`tests/`、通常の関数は`src/`へ置きます。

```text
shipping/
  seseragi.toml
  src/
    shipping.ssrg
  tests/
    shipping.ssrg
```

```toml title="seseragi.toml"
[package]
name = "docs/shipping"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "shipping"

[test]
target = "node"
jobs = 1
```

`[exports]`の`"." = "shipping"`が公開の入口です。`[test]`の`target = "node"`は現在のテストランナーのターゲットで、アプリの`run.target`とは別の設定です。

## 公開する関数を書く

{/* example: examples/guides/testing/src/shipping.ssrg */}
```seseragi title="src/shipping.ssrg"
pub fn fee subtotal: Int -> Int =
  if subtotal >= 3000 then 0 else 400
```

関数を公開する`pub`と、モジュールを公開するexport mapの両方が必要です。テスト側はパッケージの公開入口から`fee`をimportします。

## テストの木を作る

{/* example: examples/guides/testing/tests/shipping.ssrg */}
```seseragi title="tests/shipping.ssrg"
import * as test from "std/test"
import { fee } from "docs/shipping"

pub let tests: test.Test =
  test.suite "fee" [
    test.test "below threshold"
      (test.equal 400 (fee 2999)),
    test.test "at threshold"
      (test.equal 0 (fee 3000)),
    test.test "above threshold"
      (test.equal 0 (fee 3001))
  ]
```

`test.equal`は期待値、実際の値の順です。`pub let tests: test.Test`がランナーに読み取られる入口です。ここでの`let`はテスト定義を公開する契約で、実行用の固定入力を名前だけ付けて並べる束縛とは役割が異なります。

`test.suite`と`test.test`は通常の値を作ります。テスト本文のEffectは、ランナーがそのケースを実行するまで実行されません。

## 実行する

`shipping/`で次を実行してください。

```sh
seseragi lock update
seseragi test
```

```text
PASS shipping::fee::below threshold
PASS shipping::fee::at threshold
PASS shipping::fee::above threshold
3 passed; 0 failed; 0 skipped
```

関数の条件を`subtotal > 3000`へ変えて保存したら、もう一度`seseragi lock update`を実行し、`seseragi test`で確かめてください。`at threshold`が失敗し、2 passed・1 failedになります。元の`>=`へ戻した後も、ロックを更新してからテストを実行します。

通常のソース変更はロックに含まれる内容を変えるため、更新前のテストは`SES-K0102`で止まります。テスト失敗は終了コード1、古いロックを含む設定・コンパイル・探索の問題は2です。

## 一部だけを実行する

```sh
seseragi test --filter threshold
seseragi test --exact \
  shipping::fee::at\ threshold
```

`--filter`は完全名に対する大文字小文字を区別する部分文字列です。正規表現ではありません。`--exact`は完全なケース名を指定します。どちらも0件を成功として扱わず、終了コード2になります。

`--jobs`で並列実行数を指定できます。各ケースは独立した環境とリソーススコープで実行され、レポートは定義順で出ます。

## 成功と型付き失敗を小さくテストする

送料とは別のパッケージで、名前の入力を四つのケースに分けます。[フォームの独立した検証例](/docs/guides/forms)と同じ、前後の空白を除いて空の名前を拒否する規則です。

### 名前のパッケージを用意する

```sh
mkdir -p names/src names/tests
cd names
```

次を`seseragi.toml`へ保存します。

{/* example: examples/guides/testing-validation/seseragi.toml */}
```toml title="seseragi.toml"
[package]
name = "docs/names"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "names"

[test]
target = "node"
jobs = 1
```

`src/names.ssrg`には純粋な検証関数を置きます。

{/* example: examples/guides/testing-validation/src/names.ssrg#validator */}
```seseragi title="src/names.ssrg"
import * as text from "std/text"

alias Name = Either<String, String>

pub fn name input: String -> Name = {
  let cleaned = text.trim input
  if cleaned == "" then
    Left "missing name"
  else
    Right cleaned
}
```

### 期待値と失敗理由を指定する

次の二つのコードを順に`tests/names.ssrg`へ保存します。`accepted`は期待値の型を`Either<String, String>`へ揃え、`missing`は受け入れる失敗理由を判定します。

{/* example: examples/guides/testing-validation/tests/names.ssrg#helpers */}
```seseragi title="tests/names.ssrg"
import * as test from "std/test"
import * as effects from "std/effect"
import { name } from "docs/names"

alias Name = Either<String, String>

fn accepted value: String -> Name =
  Right value

fn missing error: String -> Bool =
  error == "missing name"
```

正常な入力には`test.equal`を使います。空入力には`test.expectFailure`を使い、型付き失敗になることと、その理由の両方を確かめます。

{/* example: examples/guides/testing-validation/tests/names.ssrg#cases */}
```seseragi title="tests/names.ssrg"
pub let tests: test.Test =
  test.suite "name" [
    test.test "valid" $
      test.equal (accepted "Ada") $
        name "Ada",
    test.test "trimmed" $
      test.equal (accepted "Ada") $
        name " Ada ",
    test.test "blank" $
      name ""
      |> effects.fromEither
      |> test.expectFailure missing,
    test.test "spaces" $
      name "   "
      |> effects.fromEither
      |> test.expectFailure missing
  ]
```

```sh
seseragi lock update
seseragi test
```

```text
PASS names::name::valid
PASS names::name::trimmed
PASS names::name::blank
PASS names::name::spaces
4 passed; 0 failed; 0 skipped
```

`blank`と`spaces`は、検証が失敗したことを確認してテストが成功するケースです。検証の`Either`は`effects.fromEither`でEffectへ移しています。

### 失敗したテストを読む

`valid`の期待値だけを`accepted "Eve"`へ変え、ロックを更新して`seseragi test --filter valid`を実行すると、期待した`Right "Eve"`と実際の`Right "Ada"`の不一致が出ます。期待値を戻してから、次の変更を一つずつ試せます。

| 変更 | `blank`が報告する問題 |
| --- | --- |
| 空入力で`Right "default"`を返す | `expected a typed failure` |
| `missing`が別の理由を求める | `typed failure did not match` |

どちらもロックを更新した後、`seseragi test --filter blank`で確かめられます。前者は失敗するはずの処理が成功した場合、後者は失敗したが理由が違った場合です。テストの終了コードは1です。試した変更を元へ戻すたびに、ロックを更新して四件が通ることを確認してください。

`expectFailure`は型付き失敗を検証するための関数です。defectやキャンセルを、期待した入力エラーとして成功扱いにはしません。

## 検証する範囲を選ぶ

このテストは送料の規則を検証し、フォームの入力やブラウザーの操作は検証しません。UIの入力・フォーカス・イベントの確認は、ブラウザーでも行います。純粋な更新関数は同じ`test.equal`で直接確認できます。

[状態とAction](/docs/guides/state-and-actions)にUIから分けた更新関数の例があります。ランナーのtimeout、filter、終了コードは[CLI Reference](/docs/reference/cli)で確認できます。
