---
title: テストを書く
description: 公開APIをstd/testで検証し、境界値を継続して確かめる。
---

小計が3000以上なら送料0、それより少なければ400を返す関数をテストします。境界の少し手前・ちょうど境界・少し先の三つをテストしておけば、あとで条件を書き間違えてもすぐに気づけます。

## テスト用のパッケージを作る

`shipping/`に次のファイルを作ります。関数は`src/`に、テストは`tests/`に置きます。

```text
shipping/
  seseragi.toml
  src/
    shipping.ssrg
  tests/
    shipping.ssrg
```

```toml title="seseragi.toml"
[package]
name = "docs/shipping"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "shipping"

[test]
target = "node"
jobs = 1
```

`[exports]`の`"." = "shipping"`で、`shipping`モジュールをパッケージの入口として公開します。`[test]`の`target = "node"`はテストを実行する環境の指定で、アプリを実行する`[run]`の`target`とは別です。

## 公開する関数を書く

{/* example: examples/guides/testing/src/shipping.ssrg */}
```seseragi title="src/shipping.ssrg"
pub fn fee subtotal: Int -> Int =
  if subtotal >= 3000 then 0 else 400
```

テストからは、パッケージの外から使うのと同じように`fee`をimportします。そのため、関数の`pub`と、`[exports]`でのモジュールの公開の両方が必要です。

## テストの木を作る

{/* example: examples/guides/testing/tests/shipping.ssrg */}
```seseragi title="tests/shipping.ssrg"
import * as test from "std/test"
import { fee } from "docs/shipping"

pub let tests: test.Test =
  test.suite "fee" [
    test.test "below threshold"
      (test.equal 400 (fee 2999)),
    test.test "at threshold"
      (test.equal 0 (fee 3000)),
    test.test "above threshold"
      (test.equal 0 (fee 3001))
  ]
```

`test.equal`の引数は、期待する値、実際の値の順です。テストランナーは、`pub let tests: test.Test`という名前の値を探して実行します。

`test.suite`と`test.test`は、テストの一覧を表す普通の値を作るだけです。テストの中身は、ランナーがそのテストを実行するときに初めて実行されます。

## 実行する

`shipping/`で次のコマンドを実行します。

```sh
seseragi lock update
seseragi test
```

```text
PASS shipping::fee::below threshold
PASS shipping::fee::at threshold
PASS shipping::fee::above threshold
3 passed; 0 failed; 0 skipped
```

試しに、関数の条件を`subtotal > 3000`に変えてみてください。保存したら`seseragi lock update`を実行してから`seseragi test`を実行します。`at threshold`が失敗し、2 passed・1 failedになります。確かめたら`>=`に戻し、同じようにロックファイルを更新してからテストします。

ソースを変えるとロックファイルの内容と合わなくなるので、更新しないままだと`SES-K0102`で止まります。終了コードは、テストの失敗なら1、ロックファイルの不一致やコンパイルエラーなどなら2です。

## 一部だけを実行する

```sh
seseragi test --filter threshold
seseragi test --exact \
  shipping::fee::at\ threshold
```

`--filter`には、テストの名前に含まれる文字列を指定します（大文字と小文字は区別し、正規表現は使えません）。`--exact`は、テストの名前を完全に指定します。どちらも、一致するテストが一件もなければ終了コード2で終わります。

`--jobs`で、同時に実行するテストの数を指定できます。並べて実行しても、結果は定義した順に表示されます。

## 成功と型付き失敗を小さくテストする

次は、失敗することを確かめるテストです。別のパッケージで、[フォーム](/docs/guides/forms)の検証と同じ「前後の空白を取り除き、空なら受け付けない」規則を、四つの入力でテストします。

### 名前のパッケージを用意する

```sh
mkdir -p names/src names/tests
cd names
```

`seseragi.toml`は次のとおりです。

{/* example: examples/guides/testing-validation/seseragi.toml */}
```toml title="seseragi.toml"
[package]
name = "docs/names"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "names"

[test]
target = "node"
jobs = 1
```

`src/names.ssrg`に検証の関数を書きます。

{/* example: examples/guides/testing-validation/src/names.ssrg#validator */}
```seseragi title="src/names.ssrg"
import * as text from "std/text"

alias Name = Either<String, String>

pub fn name input: String -> Name = {
  let cleaned = text.trim input
  if cleaned == "" then
    Left "missing name"
  else
    Right cleaned
}
```

### 期待値と失敗理由を指定する

次の二つのコードを順に`tests/names.ssrg`に書きます。`accepted`は期待する成功の値を作る関数、`missing`は期待する失敗の理由かどうかを判定する関数です。

{/* example: examples/guides/testing-validation/tests/names.ssrg#helpers */}
```seseragi title="tests/names.ssrg"
import * as test from "std/test"
import * as effects from "std/effect"
import { name } from "docs/names"

alias Name = Either<String, String>

fn accepted value: String -> Name =
  Right value

fn missing error: String -> Bool =
  error == "missing name"
```

正しい入力には`test.equal`を使います。空の入力には`test.expectFailure`を使い、失敗することと、失敗の理由の両方を確かめます。

{/* example: examples/guides/testing-validation/tests/names.ssrg#cases */}
```seseragi title="tests/names.ssrg"
pub let tests: test.Test =
  test.suite "name" [
    test.test "valid" $
      test.equal (accepted "Ada") $
        name "Ada",
    test.test "trimmed" $
      test.equal (accepted "Ada") $
        name " Ada ",
    test.test "blank" $
      name ""
      |> effects.fromEither
      |> test.expectFailure missing,
    test.test "spaces" $
      name "   "
      |> effects.fromEither
      |> test.expectFailure missing
  ]
```

```sh
seseragi lock update
seseragi test
```

```text
PASS names::name::valid
PASS names::name::trimmed
PASS names::name::blank
PASS names::name::spaces
4 passed; 0 failed; 0 skipped
```

`blank`と`spaces`は、検証がちゃんと失敗したので、テストとしては成功です。検証結果の`Either`は、`effects.fromEither`でEffectに変えてから渡しています。

### 失敗したテストを読む

`valid`の期待値を`accepted "Eve"`に変え、ロックファイルを更新して`seseragi test --filter valid`を実行すると、期待した`Right "Eve"`と実際の`Right "Ada"`が違う、と表示されます。期待値を戻したら、次の二つの変更も一つずつ試せます。

| 変更 | `blank`が報告する問題 |
| --- | --- |
| 空入力で`Right "default"`を返す | `expected a typed failure` |
| `missing`が別の理由を求める | `typed failure did not match` |

どちらも、ロックファイルを更新してから`seseragi test --filter blank`で確かめます。一つ目は「失敗するはずが成功した」場合、二つ目は「失敗したが理由が違った」場合で、どちらもテストは失敗し、終了コード1になります。変更を戻したら、ロックファイルを更新して四件すべてが通ることを確かめてください。

`expectFailure`が受け止めるのは、型で表した失敗だけです。バグによる異常（defect）やキャンセルを、期待した失敗として扱うことはありません。

## 検証する範囲を選ぶ

ここでのテストは関数の動きを確かめるもので、画面の操作は確かめません。入力欄やクリックの動きは、ブラウザーで確かめます。ただし、画面の`update`のような関数なら、同じ`test.equal`でそのままテストできます（[状態とAction](/docs/guides/state-and-actions)）。テストランナーのタイムアウトやフィルター、終了コードの詳細は[CLIリファレンス](/docs/reference/cli)にあります。
