---
title: 状態とAction
description: 更新規則を純粋関数へまとめ、画面や副作用から独立して検証する。
---

カウンターの「増やす」と「戻す」を、画面なしで検証します。状態がどの操作でどう変わるかを純粋な`update`へ集めると、UIを作る前に規則を確認できます。

[Webアプリを作る](/docs/guides/web-app)のカウンターで使う更新規則を扱います。Actionのケースと`match`は[代数的データ型](/docs/learn/algebraic-data-types)と[パターンマッチ](/docs/learn/pattern-matching)の構文です。

## 現在値と操作を分ける

この例の状態は現在の数を表す`Int`です。`Action`は`Increment`と`Reset`の二つで、過去に何が起きたかを渡します。`update action state`は新しい状態を返します。

イベント名と状態を同じ型に混ぜません。たとえば`Reset`という操作を受けた結果の状態は、`Reset`という値ではなく`0`です。

## 完成した更新例

`state.ssrg`へ保存してください。

{/* example: examples/guides/state.ssrg */}
```seseragi title="state.ssrg"
type Action =
  | Increment
  | Reset

fn update action: Action -> n: Int
  -> Int =
  match action {
    Increment -> n + 1
    Reset -> 0
  }

pub effect fn main = do {
  0
  |> update Increment
  |> update Increment
  |> show
  |> println
  5
  |> update Reset
  |> show
  |> println
}
```

`update Increment`は残りの状態を受け取る関数です。そのため、`0 |> update Increment`は`update Increment 0`と同じ計算になります。

## 操作の列を実行する

```sh
seseragi run state.ssrg
```

```text
2
0
```

最初のパイプラインは0へ二回`Increment`を適用します。次は5へ`Reset`を適用します。`println`以外の処理に副作用はなく、同じ入力から同じ結果が得られます。

## 複数の値をまとめて状態にする

フォームでは現在値だけでなく、編集中の文字列や表示メッセージをまとめて持てます。`Model`は名前を持つstructです。新しい状態を作るときは、`Model { ...model, draft: value }`のようにstructの新しい値を作ります。

`let`で束縛したstructのフィールドへ代入して更新することはできません。構造を広げる具体例は[フォーム](/docs/guides/forms)にあります。

## 副作用の位置を決める

純粋な`update`の中で入力や通信を実行することはできません。`dom.app`を使う場合、更新関数はActionと状態から次の状態を返す契約です。

外部操作が必要になったら、Effectを実行するdispatchと状態の更新を分けます。`MutableSignal`へ`signals.update`を適用する例は[状態を持つ機能](/docs/guides/stateful-features)にあります。外部操作の結果をActionへ戻す設計では、成功と失敗の両方をActionのケースに含めます。

## 更新規則をテストする

UIのボタンを毎回押して確認する代わりに、`update Increment 0`が1になることや、`update Reset 5`が0になることをテストへ置けます。

[テスト](/docs/guides/testing)では`std/test`の実行手順を扱います。Actionに新しいケースを追加した場合は`match`の網羅性もコンパイラーが確認します。構文の詳しい契約は[パターン Reference](/docs/reference/patterns)で調べられます。
