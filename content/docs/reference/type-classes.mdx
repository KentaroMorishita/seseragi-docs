型クラスは、ある型がどんな操作を持っているかを表します。クラスの継承や、実行時のオブジェクトのinterfaceとは違い、どの実装（instance）を使うかは型チェックのときに一つに決まります。

## traitとinstance

traitはメソッドの型を宣言し、instanceが本体を与えます。次の例では、`Topic`の値を表示する操作を`Label`で抽象化しています。

{/* example: examples/reference/type-classes.ssrg */}

```seseragi title="type-classes.ssrg"
trait Label<A> {
  fn label value: A -> String
}

newtype Topic = String

instance Label<Topic> {
  fn label topic: Topic -> String =
    match topic {
      Topic name -> name
    }
}

fn heading<A> value: A -> String
where Label<A> =
  label value

pub effect fn main =
  Topic "Language"
  |> heading
  |> println
```

出力は`Language`です。`instance Label<Topic>`の中の関数の型は、traitの`A`を`Topic`に置き換えた型と一致していなければなりません。

`impl Topic`は、その型だけのメソッドを書くためのものです。traitを実装するときは`instance`を使います。`impl Label<Topic>`と書くと`SES-T0502`エラーになります。

## 制約とinstanceの選ばれ方

`where Label<A>`は、「この関数を呼ぶときには、`A`の`Label`のinstanceが必要」という制約です。呼ぶ側で具体的な型が決まると、その型のinstanceが選ばれて関数に渡されます。

同じ名前の関数を持つtraitがいくつも見えていて、型からどのtraitか決められないときは、`Functor.map`のようにtrait名を付けて書きます。実行中に値を調べてinstanceを探すことはありません。

standard コレクションの`Show`などは要素型のinstanceも必要です。空Arrayや`Nothing`であっても、値を見て要素のconstraintを省略しません。必要なinstanceがない場合は`SES-T0201`です。

### ジェネリックな関数と制約

{/* example: examples/reference/typeclass-variants.ssrg#constraints */}

```seseragi title="宣言: Show constraint"
fn display<A> value: A -> String
where Show<A> =
  show value
```

{/* example: examples/reference/typeclass-variants.ssrg#show-cases */}

```seseragi title="main内: 具体型で呼ぶ"
println $ display 42
println $ display True
```

`Int`と`Bool`の`Show`のinstanceがそれぞれ選ばれ、42と`True`が出力されます。

whereを省いた次の宣言は、genericなAにShowの証拠がなく、`SES-T0201`です。これは意図的なエラー例です。

{/* example: examples/reference/invalid/missing-constraint.ssrg#invalid */}

```seseragi title="意図的なconstraintエラー"
fn display<A> value: A -> String =
  show value

pub effect fn main =
  display 42
  |> println
```

## instanceは一つだけ

一つの型に対する同じtraitのinstanceは、プログラム全体で一つしか書けません。instanceを書けるのは、traitを宣言したモジュールか、対象の型を宣言したモジュールだけです。関数の中だけで使うinstanceや、候補が複数あるときの優先順位といった仕組みはありません。

aliasはinstance identityを作りません。aliasと展開先に別のinstanceを定義して回避することはできません。匿名レコードやタプルへuser-definedなstructural instanceを追加することもできません。

標準の`Iterable<C, A>`では`C`が決まれば`A`が一つに決まり、算術のtraitでは引数の型から結果の型が一つに決まります。この決まりに反するinstanceもエラーです。自分で作るtraitにこうした決まりを宣言する構文は、今はありません。

## 標準traitと演算子

| trait | 操作・構文 |
| --- | --- |
| `Eq<A>` | `eq`、`==`、`!=` |
| `Ord<A>` | `compare`、順序比較 |
| `Show<A>` | `show`、テンプレート埋め込み |
| `Hash<A>` | ハッシュを使うコレクションのためのハッシュ値 |
| `Functor<F>` | `map`、`<$>` |
| `Applicative<F>` | `pure`、`apply`、`<*>` |
| `Monad<M>` | `flatMap`、`>>=`、`do` |
| `Add<L, R, O>`など | 算術演算子 |

`F<_>`や`M<_>`は「型引数を一つ受け取る型」を表し、`Functor<Maybe>`や`Monad<Effect<R, E, _>>`のように使います。`Ord`はすべての値に一貫した順序が必要なので、`NaN`のある`Float`には標準の`Ord`がありません。

struct/newtypeの`impl`内の標準`operator`宣言は、対応する標準trait instanceの糖衣です。独自symbolや優先順位は別のトップレベル`operator`宣言で定義します。

### 同じmapを複数の型へ使う

`increment`は`Int`に1を足す関数です。`raise`はArray・Maybe・Listのどれかに決めず、`Functor`の制約だけを持ちます。

{/* example: examples/reference/typeclass-variants.ssrg#functor */}

```seseragi title="宣言: 型構築子parameter"
fn raise<F<_>> values: F<Int>
  -> F<Int>
where Functor<F> =
  map increment values
```

{/* example: examples/reference/typeclass-variants.ssrg#instances */}

```seseragi title="main内: 三つのinstance"
println $ show $ raise [1, 2]
println $ show $ raise $ Just 2
println $ show $ raise `[3, 4]
```

順に`[2, 3]`、`Just 3`、`` `[4, 5] ``が出力されます。どのinstanceを使うかは、渡した値の型から決まります。

## derivingと型クラスの性質

`deriving`で自動で作れるのは、`Eq`・`Ord`・`Show`・`Debug`・`Hash`・`JsonEncode`・`JsonDecode`です。フィールドやペイロードの型にも、同じtraitのinstanceが必要です。型パラメーターを持つ型なら、その型パラメーターにも同じ条件が付きます。

`Hash`を作るには、同じ型の`Eq`も必要です。`deriving`と手書きの`instance`で同じものを二回定義するとエラーです。自動で作った`Ord`は、まずケースを宣言した順に比べ、同じケースならペイロードを先頭から順に比べます。newtypeの`Show`は、コンストラクター名も表示します。

`Eq`・`Ord`・`Functor`・`Applicative`・`Monad`などには、instanceが満たすべき性質（「`a == a`は必ず`True`」など）があります。コンパイラーはこれを確かめないので、[テスト](/docs/guides/testing)で確かめてください。

### 導出したEqを使う

{/* example: examples/reference/typeclass-variants.ssrg#deriving */}

```seseragi title="宣言: deriving"
newtype Tag deriving Eq, Show =
  String
```

{/* example: examples/reference/typeclass-variants.ssrg#equality */}

```seseragi title="main内: derived Eq"
Tag "docs" == Tag "docs"
|> show
|> println
```

同じ中身の`Tag`どうしを比べているので、出力は`True`です。`Tag`と`String`が同じ型として扱われることはありません。

## do記法

`do`は、一つの`Monad`の処理を順につなげる書き方です。Effect専用の構文ではありません。

```seseragi title="doの構文"
do {
  value <- wrapped
  let next = value + 1
  pure next
}
```

`<-`は中の値を取り出して名前を付け、`let`は普通の値に名前を付けます。途中に書いた式は、結果を捨てて次に進みます。最後の式が`do`全体の結果になり、省略できません。

一つの`do`の中の式は、すべて同じMonadでなければなりません。EffectのdoでEitherを使うなら、`fromEither`などで変換します。`<-`の左側のパターンは必ず一致するものに限られます（[パターン](/docs/reference/patterns)）。

### Maybeのdo

二つの`Maybe`の中身を足し、結果を`Maybe`で返す関数です。

{/* example: examples/reference/do-variants.ssrg#maybe-do */}

```seseragi title="宣言: Maybeの合成"
fn sum left: Maybe<Int>
  -> right: Maybe<Int>
  -> Maybe<Int> = do {
  a <- left
  b <- right
  pure (a + b)
}
```

{/* example: examples/reference/do-variants.ssrg#maybe-results */}

```seseragi title="main内: 成功と欠如"
sum (Just 2) (Just 3)
|> show
|> println
sum Nothing (Just 3)
|> show
|> println
```

出力は`Just 5`と`Nothing`です。

### Arrayのdo

{/* example: examples/reference/do-variants.ssrg#array-do */}

```seseragi title="宣言: Arrayの組み合わせ"
fn choices -> Array<Int> = do {
  first <- [1, 2]
  second <- [10, 20]
  pure (first + second)
}
```

{/* example: examples/reference/do-variants.ssrg#array-results */}

```seseragi title="main内: Arrayの結果"
choices ()
|> show
|> println
```

出力は`[11, 21, 12, 22]`です。一つ目のArrayが外側、二つ目のArrayが内側のループのように組み合わされます。

今のコンパイラーには、Effectの`do`の中の`let`に、別のMonadの`do`を直接書けないという制限があります。上の例のように、別の関数に分ければ使えます。
