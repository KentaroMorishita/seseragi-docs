アプリは、「HTTPを使う」「時計を使う」といったサービスを型で要求します。それを実際にどの環境のAPIで動かすかは、Providerの設定で決めます。ライブラリを追加しただけで、アプリの動かし方が勝手に変わることはありません。

## 四つの層

| 層 | 責務 |
| --- | --- |
| 標準ライブラリやパッケージのAPI | アプリが使う型、Effect、失敗の型、値の整え方 |
| Providerの契約（Contract） | サービスの名前、操作、入力・成功・失敗の形 |
| ランタイムとの橋渡し | 生成したコードとの値の受け渡しと呼び出し方 |
| ランタイムProvider | 実行環境のAPIや外部ライブラリの呼び出し |

アプリが呼ぶのは、公開されたモジュールの関数だけです。サービスの内部や橋渡しの仕組みを直接呼ぶことはありません。

## サービスとターゲット

| モジュール | 要件フィールド | サービス identity |
| --- | --- | --- |
| `std/clock` | `clock` | `std/clock::Clock` |
| `std/fs` | `fileSystem` | `std/fs::FileSystem` |
| `std/http` | `httpClient` | `std/http::HttpClient` |
| `std/http/server` | `httpServer` | `std/http/server::HttpServer` |
| `std/web/dom` | `dom` | `std/web/dom::Dom` |
| `std/web/storage` | `storage` | `std/web/storage::Storage` |

アプリが必要とするサービスは、Effectの型から集められ、`main`の必要なものとしてまとめられます。importしただけで使っていないサービスが、必要なものに加わることはありません。

`seseragi.toml`に書く`process`や`web`は、アプリをどこで動かすかを表すターゲットです。Providerの成果物に付いている`bun-process`のような名前は、それとは別の、実際の実行環境の名前です。まずターゲットを決め、そのあとでProviderが選ばれます。Providerが足りないからといって、勝手に別のターゲットに切り替わることはありません。今は、`process`はBunで、`web`はブラウザーで動きます。なお、コンパイラーがWASMで配られていることと、生成されるプログラムがWASMになることは別の話です。

## Clockを使う例

次のパッケージは時計（Clock）のサービスを使い、`Clock ready`と出力します。

{/* example: examples/reference/provider-clock/src/main.ssrg */}

```seseragi title="main.ssrg"
import * as clock from "std/clock"

pub effect fn main = do {
  _ <- clock.now ()
  println "Clock ready"
}
```

この例の`seseragi.toml`は、ターゲットに`process`を選び、`[providers]`でサービス`std/clock::Clock`にProvider`seseragi/runtime-bun#clock`を指定しています。指定を省くと、ターゲットごとの既定のProviderが使われます。Providerの指定は動かし方の設定で、アプリの関数の型にProviderの名前が出てくることはありません。

## 候補と互換性

Providerの候補になるのは、選んだターゲットに標準で用意されているものか、アプリが直接依存しているパッケージが公開しているものです。間接的に依存しているライブラリは、サービスを要求することはできますが、アプリの代わりにProviderを選ぶことはできません。

候補は、サービス・ターゲット・契約のバージョン・ランタイムとの橋渡しのバージョン・必要な機能・TypeScript側のパッケージの解決を、すべて満たしていなければなりません。契約のメジャーバージョンは一致し、マイナーバージョンは必要なもの以上でなければなりません。パッケージのバージョンと、契約や橋渡しのバージョンは別物です。

## 選択と事前エラー

条件を満たす候補の中から、アプリの`seseragi.toml`での指定、ターゲットの既定、候補が一つだけならそれ、の順で選ばれます。指定や既定が条件を満たさなくても、別の候補に勝手に切り替わることはありません。指定がなく、候補が一つもなければ「見つからない」、二つ以上あれば「決められない」というエラーになります。

| code | 原因 |
| --- | --- |
| `SES-K0201` | サービスのProviderがない |
| `SES-K0202` | 互換候補が複数あり曖昧 |
| `SES-K0203` | 選択Providerのターゲットが不一致 |
| `SES-K0204` | Contract バージョンが不適合 |
| `SES-K0205` | バックエンド/ABIが不適合 |
| `SES-K0206` | ランタイム feature/host パッケージが不足 |
| `SES-K0207` | 要件のContract majorが衝突 |
| `SES-K0208` | 明示/defaultのidentityが候補として不可視 |

Providerの選択は、プログラムを実行する前に終わります。用意できないサービスを`undefined`のまま実行して、途中でエラーになるようなことはありません。選んだProviderの情報は`seseragi.lock`に記録されます。

## 実行とリソース

Providerを使うEffectも、作っただけでは実行されません。失敗・defect・キャンセルは、それぞれ別の終わり方として扱われます。リソースを取得してから後始末を登録するまでの間に取りこぼしは起きず、自分で閉じたあとに後始末が動いても、閉じる処理は一回だけです。

リソースやコールバックは、使う側のスコープが終わるときに解除されます。ガベージコレクションやモジュールのグローバル変数に後始末を任せることはしません。Providerを自分で作る場合は、データの形・互換性・後始末についての決まりを満たす必要があります。

アプリが必要とするものの組み立て方は[Effect](/docs/reference/effects)、設定とロックファイルの更新は[プロジェクト設定](/docs/reference/project-configuration)、モジュールごとの対応ターゲットは[標準ライブラリ](/docs/reference/library)にあります。
