性能については、「言語として保証していること」「理論上は実行時に消せる仕組み」「コンパイラーが実際にどこまで最適化するか」を分けて考えます。理論上消せる仕組みがあるからといって、どのプログラムでも最速のJavaScriptになるとは限りません。

## コードから分かるコスト

| 書き方 | 実行時にかかる仕事 |
| --- | --- |
| alias、型引数、パイプライン、`$` | それ自体には実行時のコストはない |
| ラムダ、部分適用 | 外の変数を覚えるクロージャが作られることがある |
| traitの制約 | 型チェックで選ばれる。ジェネリックな関数ではinstanceの受け渡しが残ることがある |
| map/filter/reduce、Show、JSON、SSR | 入力の大きさや途中で止まる位置に応じた走査 |
| Effect、Stream、Signal、画面の表示 | 実行の順番待ち、購読、後始末 |
| TypeScriptとの値の受け渡し | 安全のための検査とコピー |

関数が同じものかどうかや、値が実行時にどんなオブジェクトになっているかは、プログラムからは分かりません。そのため、コンパイラーは結果・評価の順番・失敗・キャンセル・リソース・外とのやり取りを変えない範囲で、値の表し方を自由に変えられます。

## ArrayとList

Arrayは要素が一続きに並んだ列、Listは要素をつないだリストで、どちらも書き換えられません。Listの先頭に要素を足すことと、先頭以外を取り出すことは、長さに関係なく一瞬でできます。Arrayのパターンの`...rest`は残りのArrayをコピーするので、`[head, ...tail]`で再帰を繰り返すと、全体で要素数の二乗に比例する時間がかかります。

大きなArrayを最後まで処理するときは、`reduce`や`reduceUntil`などのコレクションの関数を使います。途中で止まる関数は、止まった位置より後ろの要素には関数を呼びません。ArrayとListの変換や、TypeScriptとの間の値のコピーにも、コストがかかることを忘れないでください。

map/filterの結果はstrictです。中間コレクションを観測せず、コールバックの回数・順序・defectが同じ場合にfusionできる余地はありますが、現在のバックエンドがすべてのパイプラインをfusionする保証はありません。

## 再帰とスタック

pureな名前付き関数への、全引数を与えた直接self tail callは一定のホスト stackで実行します。次は再帰の結果へ後処理を残さず、引数を更新して次へ進む例です。

{/* example: examples/reference/performance.ssrg */}

```seseragi title="performance.ssrg"
fn sum total: Int
  -> next: Int -> Int =
  if next == 0 then
    total
  else
    sum (total + next) (next - 1)

pub effect fn main =
  sum 0 100
  |> show
  |> println
```

development/releaseの両方で5050を出力することを確認しています。tail位置は最終式やif/matchの最終分岐を含みます。相互再帰、部分適用したself call、ラムダ内からの呼び出し、`1 + recursiveCall`のようなnon-tail callには同じ保証がありません。

Effectの末尾再帰は、普通の関数のようにループに置き換えられるわけではなく、Effectの仕組みの中で続きを実行します。それでも、長い`do`や、要素を一つずつ順に処理するEffectで、スタックが入力の長さに比例して増えることはありません。

## Effect、Signal、DOM

コンパイラーは、順に実行するEffectを勝手に並列にしたり、リソースの取得・解放やキャンセルの確認をまたいで処理を動かしたりはしません。購読やイベントリスナーは、ガベージコレクションに任せず、スコープが終わるときに解除します。

Signalは、一回の書き換えで影響を受ける計算を、それぞれ多くても一回だけやり直し、すべて終わってから通知します。画面は、変わらない部分・値だけが変わる部分・構造が変わる部分を分けて書けるので、変わらない部分まで毎回作り直すことはありません。

ただし、「画面の更新回数がいつも最小」「クロージャがすべて消える」「ジェネリックな関数がすべて型ごとに特殊化される」といった最適化は保証していません。メモリの割り当て回数を減らすために、必要な値や購読を早く手放してはいけません。

## releaseビルドの成果物

```bash
seseragi build . --profile release
seseragi build . --source-map emit
```

developmentかreleaseかで、プログラムの動きは変わりません。今のreleaseビルドでは、CLIアプリはランタイムを含む`entry.js`を、Webアプリは`assets/app.js`を作ります。ただし、TypeScriptのbindingを使うCLIアプリは複数のファイルになるので、いつも一つのファイルになるわけではありません。

`artifact-manifest.json`には、実際の入口のファイル、コンパイラー・ランタイム・バンドラーのバージョン、各ファイルの大きさとハッシュ、ソースマップの設定、行ったバンドルや解析の結果が記録されます。行っていない計測や解析は`null`になり、「0バイトだった」とは区別されます。

今のreleaseビルドでは、コードの圧縮（minify）と、使われていないコードの除去を行います。ただし、コンパイラーが「使われていない」と判断した宣言の一覧と、最終的なファイルに残ったコードは別物です。Providerの起動処理やタイムゾーンのデータのように、今は削れないコストもあります。

## 計測と比較

`std/benchmark`でベンチマークを書き、`seseragi benchmark`でウォームアップ・計測回数・比較の基準を管理します。比べるときは、入力の大きさ、コンパイラー・ランタイム・実行環境のバージョン、プロファイル、乱数のシードをそろえ、プログラムの動きを変えないまま、時間・メモリの割り当て・処理量を比べます。

```bash
seseragi benchmark . --target node \
  --warmup 10 --samples 50 \
  --minimum-sample-ms 100
```

benchmark bodyは実行するたびに新しく計算し、必要なら`blackBox`で入力・結果を観測可能な境界へ渡します。一度計算した結果の取得時間だけを測る構成にはしないでください。baselineの比較だけで、typed failureやリソース cleanupが保たれたことまでは証明できません。

関数ごとの計算量は[標準ライブラリ](/docs/reference/library)、ベンチマークやテストの書き方は[テスト](/docs/guides/testing)にあります。
