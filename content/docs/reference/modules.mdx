`.ssrg`ファイル一つが一つのmoduleです。source内にmodule名は書きません。通常のidentityはpackage identityとsource rootからの相対module pathで決まり、ファイルの絶対pathでは決まりません。

## 公開範囲

宣言は既定でmodule-privateです。他のmoduleから使う`fn`、`let`、`type`、`struct`、`newtype`、`alias`、`trait`などへ`pub`を付けます。公開署名からprivate型を漏らすことはできません。

公開ADT/newtypeのconstructorと公開structのfieldは、通常は型と一緒に公開されます。`pub opaque`を使うと、他moduleには型名と公開operationだけを渡し、constructor・field・分解を定義module内へ隠せます。

inherent methodも既定ではprivateです。trait instance自体へ`pub`は付けません。instanceのmoduleがtransitive import closureへ含まれると、instance探索の対象になります。

## importと二つのファイル

`labels.ssrg`は、型と表示関数を公開するmoduleです。次は宣言ファイルの内容です。

```text title="src/labels.ssrg"
pub type Stage =
  | Draft
  | Published String

pub fn title stage: Stage -> String =
  match stage {
    Draft -> "Draft"
    Published name -> name
  }
```

同じsource directoryの`main.ssrg`から、公開名だけをimportします。この二fileのpackageを実行すると`Seseragi`を出力します。

{/* example: examples/reference/modules-project/src/main.ssrg */}

```seseragi title="main.ssrg"
import { Published, title }
  from "./labels"

pub effect fn main =
  Published "Seseragi"
  |> title
  |> println
```

importはmodule先頭へ置きます。別名を付ける`import { parse as parseText }`と、`import * as text from "std/text"`のnamespace importも使えます。namespace importは`text.trim`のような修飾参照だけを導入し、全名をunqualifiedにするwildcard構文はありません。

## specifierの解決

| 先頭形式 | 解決先 |
| --- | --- |
| `./`、`../` | 現在moduleと同じroot内の相対file |
| `self/` | 現在packageのprivate source module |
| `std/` | canonical standard module |
| `gen/` | 現在packageのgenerated binding |
| bare specifier | 宣言済みの直接dependencyと公開subpath |

`./labels`は正確に`labels.ssrg`へ解決します。directory index、別拡張子、working directoryへのfallbackはありません。source/test/generated rootを相対importで横断することもできません。

dependencyではexport mapにあるsubpathだけ使えます。transitive dependencyを直接importする場合も、自分のmanifestへ直接dependencyとして宣言します。[プロジェクト設定](/docs/reference/project-configuration)でlayoutとexport mapを確認できます。

## re-exportと名前空間

`pub import { Name } from "./module"`は元のidentityを保ったまま公開APIへ加えます。`pub import * as tools from "./tools"`は公開namespaceを導入します。

型/trait、値/関数/constructor、field/method、module alias、独自operatorは別namespaceです。newtypeの型とconstructorが同じspellingでも、一つのnamed importで両方を導入できます。

unqualified名はlocal binding、現在moduleの宣言、明示import、preludeの順に探します。同じnamespace・同じ段階の重複を勝手に選びません。operatorは`import { operator <+> }`で別にimportし、fixityもinterfaceから取得します。

## 循環と初期化

型だけのimportでもmodule graphの循環は禁止です。相互参照する共有型は第三moduleへ分け、同一moduleの関数相互再帰は`rec`へまとめます。

moduleはdependency順に一度だけ初期化し、top-level `let`はsource順に評価します。後続の`let`を初期化前に読む呼び出しは`SES-N0201`です。同じmoduleを複数箇所からimportしてもtop-level値を二度作りません。

importでSeseragiのEffectは実行しません。foreign moduleのload modeは別の明示契約です。[TypeScript連携](/docs/reference/typescript-interop)を参照してください。

## 実行module

実行packageは`run.entry`から公開`main`を一つ解決します。`main`のsuccessは`Unit`、requirementはclosed recordです。library packageに`main`は不要で、importしたmoduleの`main`を暗黙に実行することもありません。

単一fileのscratch実行ではpackage dependencyや複数fileのgraphを推測しません。このページの二file例のようなアプリは、manifestとlockを持つpackageで実行してください。[packageを作る](/docs/guides/packages-and-deployment)で手順を説明しています。
