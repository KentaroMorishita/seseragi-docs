同じ`map`がArrayにもMaybeにも使えるのは、それぞれの型が`map`の実装を持っているからです。このように「この操作ができる型」をまとめる仕組みを型クラスと呼びます。TypeScriptの`interface`に近いですが、型クラスは値ではなく型に対して実装を結び付けます。

この章では、標準の型クラスを使ってから、値を表示する自分の型クラスを作ります。

この章のコードでは、[パイプライン](/docs/learn/pipelines)の`|>`と`show`、[関数適用演算子](/docs/learn/application-operator)の`$`、[レコードとstruct](/docs/learn/records-and-structs)、[代数的データ型](/docs/learn/algebraic-data-types)、[ジェネリクス](/docs/learn/generics)、[Effect](/docs/learn/effects)の`do`を使います。

## 標準の操作を制約として使う

これまで使ってきた`==`は、`Eq`という型クラスの操作です。ジェネリックな関数で`==`を使うには、「`A`は`Eq`を実装している」という条件を`where`で書きます。

{/* example: examples/learn/focused/type-class-eq.ssrg#declaration */}
```seseragi title="関数の宣言"
fn same<A> left: A -> right: A
  -> Bool where Eq<A> =
  left == right
```

{/* example: examples/learn/focused/type-class-eq.ssrg#calls */}
```seseragi title="mainのdo内の式"
println $ show $ same 42 42
println $ show $ same "Aki" "Aki"
println $ show $ same [1, 2] [2, 1]
```

結果は順に`True`、`True`、`False`です。`same`の本体は同じでも、`Int`・`String`・Arrayそれぞれの`Eq`の実装が使われます。Arrayの比較では要素の順番も比べるので、最後は`False`になります。

## traitで型クラスを宣言する

ここからは、自分で型クラスを作ります。まず`trait`で、型クラスが持つ操作を宣言します。

{/* example: examples/learn/focused/type-class-instances.ssrg#trait */}
```seseragi title="traitの宣言"
trait Render<A> {
  fn render value: A -> String
}
```

次に、対象の型と、その型での実装を書きます。

{/* example: examples/learn/focused/type-class-instances.ssrg#badge */}
```seseragi title="型とinstanceの宣言"
struct Badge {
  label: String,
}

instance Render<Badge> {
  fn render value: Badge -> String =
    value.label
}
```

`trait Render<A>`は、「`A`を受け取って`String`を返す`render`という操作を持つ」という約束です。`trait`の中には型だけを書き、本体は書きません。

`instance Render<Badge>`で、`Badge`型での`render`の中身を書きます。これで`Badge`は`Render`の約束を満たします。

## whereで必要な操作を示す

次の`framed<A>`は、`where Render<A>`で「`A`は`Render`を実装していること」を条件にしています。この条件があるので、本体で`render value`を呼べます。

{/* example: examples/learn/focused/type-class-instances.ssrg#framed */}
```seseragi title="関数の宣言"
fn framed<A> value: A -> String
where Render<A> =
  `<${render value}>`
```

`Badge`を`framed`に渡してみます。

{/* example: examples/learn/focused/type-class-instances.ssrg#badge-use */}
```seseragi title="main内の式"
Badge { label: "ADMIN" }
|> framed
|> println
```

`<ADMIN>`と表示されます。

`Badge`には`Render`のinstanceがあるので、`framed`に渡せます。instanceのない型を渡すと、コンパイルエラーになります。どの実装を使うかはコンパイル時に決まり、実行中に値を調べて探すことはありません。

## 同じ操作を違う型で使う

標準の`map`は`Functor`という型クラスの操作です。Arrayなら各要素を、Maybeなら`Just`の中身を、Eitherなら`Right`の中身を変換します。どれも「外側の形はそのままで、中身だけを変換する」という同じ約束を、型ごとに実装しています。

ほかにも、`Show`は値を文字列にする操作、`Eq`は等しいかを比べる操作を持ちます。型クラスごとに決まった意味があり、名前が同じなら何をしてもよいわけではありません。

## instanceを自動で作る

`Eq`や`Show`のinstanceは、`deriving`を付けると自動で作れます。

{/* example: examples/learn/deriving.ssrg */}
```seseragi title="deriving.ssrg"
type Phase deriving Eq, Show =
  | Ready
  | Done

pub effect fn main = do {
  println $ show $ Ready == Ready
  println (show Done)
}
```

```text title="実行結果"
True
Done
```

ペイロードやフィールドを持つ型の場合、その中身の型も同じ型クラスを実装している必要があります。たとえば、`Show`を持たないフィールドがある型には、`Show`を`deriving`できません。また、自分で作った`Render`のような型クラスは`deriving`できません。

### フィールドを持つ型の導出

フィールドを持つstructにも、`Eq`と`Show`を`deriving`できます。

{/* example: examples/learn/focused/type-class-derived-fields.ssrg#declaration */}
```seseragi title="structの宣言"
struct Point deriving Eq, Show {
  x: Int,
  y: Int,
}
```

`y`だけが違う二つの値を作ります。

{/* example: examples/learn/focused/type-class-derived-fields.ssrg#values */}
```seseragi title="mainのdo内の束縛"
let left = Point { x: 1, y: 2 }
let right = Point { x: 1, y: 3 }
```

比較と表示をしてみます。

{/* example: examples/learn/focused/type-class-derived-fields.ssrg#comparison */}
```seseragi title="mainのdo内の式"
println $ show $ left == right
```

{/* example: examples/learn/focused/type-class-derived-fields.ssrg#display */}
```seseragi title="mainのdo内の式"
println $ show left
```

```text title="実行結果"
False
Point { x: 1, y: 2 }
```

自動で作られた`Eq`はフィールドを一つずつ比べ、`Show`は型名とフィールドを文字列にします。フィールドの`Int`が`Eq`と`Show`を持っているので、`Point`にも`deriving`できます。

## instanceの決まり

一つの型に、同じ型クラスのinstanceは一つしか書けません。また、instanceを書けるのは、その`trait`を宣言したモジュールか、対象の型を宣言したモジュールだけです。この決まりのおかげで、importを一つ足しただけで別の実装に切り替わってしまう、ということが起きません。

`impl Badge`に書くメソッドと、`instance Render<Badge>`は別物です。メソッドはその型だけの操作で、instanceは型クラスの約束を満たすための実装です。型クラスは、クラスの継承のような仕組みではありません。

コンパイラーが確かめるのは型までです。「`a == a`は必ず`True`」のような、型クラスが期待する性質までは確かめません。自分でinstanceを書いたときは、テストで確かめましょう。詳しくは[型クラスリファレンス](/docs/reference/type-classes)にあります。

### 二つ目のinstanceを定義する

別の型にも`Render`を実装してみます。

{/* example: examples/learn/focused/type-class-instances.ssrg#tag */}
```seseragi title="型とinstanceの宣言"
struct Tag {
  text: String,
}

instance Render<Tag> {
  fn render value: Tag -> String =
    `#${value.text}`
}
```

同じ`framed`に渡します。

{/* example: examples/learn/focused/type-class-instances.ssrg#tag-use */}
```seseragi title="main内の式"
Tag { text: "help" }
|> framed
|> println
```

`<#help>`と表示されます。`Tag`の`render`が先頭に`#`を付け、`framed`がそれを`< >`で囲みます。`framed`を書き直さなくても、instanceを足すだけで新しい型に対応できます。

## 試してみる

`Badge`と`Tag`の例を一つのファイルにまとめて、両方を`framed`に渡してみてください。そのあと`instance Render<Tag>`を消すと、`Tag`を`framed`に渡している行がエラーになることを確かめます。
