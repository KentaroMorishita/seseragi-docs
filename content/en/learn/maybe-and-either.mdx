In TypeScript, a missing value is often `undefined` or `null`, and a failure is often an exception. Neither shows up clearly in the types, so a forgotten check goes unnoticed.

Seseragi expresses both in types. When having no value is an ordinary result, as in "searched but not found", use `Maybe`. When you need to say why something failed, as in "the input was invalid", use `Either`. This chapter tries each in turn, then combines them in an example that validates a port number.

The code in this chapter uses [Functions](/en/docs/learn/functions) for lambdas, [Pipelines](/en/docs/learn/pipelines) for `|>`, [Algebraic data types](/en/docs/learn/algebraic-data-types), [Pattern matching](/en/docs/learn/pattern-matching) for `match`, and [Arrays and lists](/en/docs/learn/arrays-and-lists).

## Represent presence and absence with Maybe

`Maybe<A>` is either `Just value`, holding a value, or `Nothing`, holding none. `Just 21` means there is an integer. `Nothing` alone does not say what type is missing, so write the type when needed: `let absent: Maybe<Int> = Nothing`.

`maybeValue ?? fallback` returns the value inside a `Just`, or the fallback on the right for `Nothing`. The fallback is computed only for `Nothing`. `??` works only with `Maybe`, not with `Either`.

### Transform only when there is a value

The `map` you used with Arrays also works with `Maybe`:

{/* example: examples/learn/focused/maybe-map.ssrg#present */}
```seseragi title="Binding in main"
let present =
  Just 21
  |> map (\n -> n * 2)
```

`present` is `Just 42`. Try it without a value:

{/* example: examples/learn/focused/maybe-map.ssrg#absent */}
```seseragi title="Binding in main"
let absent: Maybe<Int> =
  Nothing
  |> map (\n: Int -> n * 2)
```

`absent` stays `Nothing`. There is nothing inside, so the lambda is not called. You write only what to do when there is a value, without checking every time.

## Preserve a failure reason with Either

`Either<E, A>` is either `Left error`, a failure, or `Right value`, a success. Here, an `Either` whose failure reason is a string and whose success value is an integer gets the alias `Result`. `alias` only gives a name; it does not create a new type.

{/* example: examples/learn/focused/either-do.ssrg#result-type */}
```seseragi title="Type alias"
alias Result = Either<String, Int>
```

{/* example: examples/learn/focused/either-map.ssrg#success */}
```seseragi title="Binding in main"
let success: Result =
  Right 21
  |> map (\n -> n * 2)
```

`success` is `Right 42`. Try a failure too:

{/* example: examples/learn/focused/either-map.ssrg#failure */}
```seseragi title="Binding in main"
let input: Result = Left "invalid"
let failure =
  input
  |> map (\n -> n * 2)
```

`failure` stays `Left "invalid"`. As with `Nothing` in `Maybe`, the lambda is not called for `Left`, and the failure reason is kept. (`Left` alone does not say what the success type is, so `input` is annotated as `Result`.)

## Chain steps that may fail

Now consider a transformation that itself returns `Maybe`. This function returns a positive integer as it is, and `Nothing` otherwise:

{/* example: examples/learn/focused/maybe-flatmap.ssrg#declaration */}
```seseragi title="Function declaration"
fn positive n: Int -> Maybe<Int> =
  if n > 0 then Just n else Nothing
```

Passing it to `map` puts a `Maybe` inside another `Maybe`:

{/* example: examples/learn/focused/maybe-flatmap.ssrg#nested */}
```seseragi title="Binding in main"
let nested =
  Just 2
  |> map positive
```

`nested` has type `Maybe<Maybe<Int>>` and prints as `Just Just 2`. When the next step also returns `Maybe`, use `flatMap` instead of `map`:

{/* example: examples/learn/focused/maybe-flatmap.ssrg#chained */}
```seseragi title="Binding in main"
let chained =
  Just 2
  |> flatMap positive
```

`chained` is `Just 2`, of type `Maybe<Int>`. Try a case where `positive` returns `Nothing`:

{/* example: examples/learn/focused/maybe-flatmap.ssrg#rejected */}
```seseragi title="Binding in main"
let rejected =
  Just (-1)
  |> flatMap positive
```

`rejected` is `Nothing`. And if the starting value is `Nothing`, `positive` is never called. The `>>=` operator does the same thing as `flatMap`.

### Write the steps in order with do

Stacking `flatMap` calls quickly becomes hard to read. That is what `do` notation is for. Combine two checks that return `Either`:

{/* example: examples/learn/focused/either-do.ssrg#validation */}
```seseragi title="Function declaration"
fn requirePositive n: Int -> Result =
  if n > 0 then
    Right n
  else
    Left "must be positive"
```

A function that adds two values only when both are positive can be written with `do`:

{/* example: examples/learn/focused/either-do.ssrg#combination */}
```seseragi title="Function declaration"
fn addChecked x: Int -> y: Int
  -> Result = do {
    left <- requirePositive x
    right <- requirePositive y
    Right (left + right)
  }
```

| Application expression | Result |
| --- | --- |
| `addChecked 2 3` | `Right 5` |
| `addChecked (-1) 3` | `Left "must be positive"` |

`left <- requirePositive x` takes the value out as `left` if the result is `Right`, and moves to the next line. If it is `Left`, it stops there, and that `Left` becomes the result of the whole function. It is similar to returning early on failure in TypeScript. The final `Right (left + right)` is the result when every step succeeds.

`do` is not reserved for Effects, which come later. Here it chains ordinary values such as `Maybe` and `Either`.

## Combine Maybe and Either

This example takes a port number from a configuration and checks that it is in range. A missing value is handled with `Maybe`, and an out-of-range value with `Either`. The failure type is `PortError`, defined in the program, rather than a string.

{/* example: examples/learn/maybe-and-either.ssrg */}
```seseragi title="maybe-and-either.ssrg"
type PortError =
  | OutOfRange Int

alias PortResult =
  Either<PortError, Int>

fn validPort n: Int -> PortResult =
  if n >= 1 && n <= 65535 then
    Right n
  else
    Left (OutOfRange n)

fn explain result: PortResult
  -> String =
  match result {
    Right port -> `Port: ${port}`
    Left (OutOfRange n) ->
      `Invalid port: ${n}`
  }

pub effect fn main = do {
  let ports = [8080]
  let candidate = ports[0] ?? 3000
  candidate
  |> validPort
  |> explain
  |> println
}
```

```text title="Output"
Port: 8080
```

`ports[0] ?? 3000` uses 3000 when there is no value. That value goes to `validPort`, which returns `Right n` for 1 through 65535 and `Left (OutOfRange n)` otherwise. Because `OutOfRange` carries the rejected value, the error message can include it.

`explain` uses `match` to handle both cases: `Right port` takes out the successful value and `Left (OutOfRange n)` takes out the rejected one, each returning text to display.

Returning `Left` does not jump away like an exception. An `Either` is just a value, so you can inspect it with `match` or pass it to other functions.

## Maybe or Either?

`Maybe` carries no reason for a missing value. When you want to say why something failed, or there are several kinds of failure, use an `Either` with an ADT as its failure type.

The port check in this chapter only takes a value and returns a result. Work such as actually connecting to the network is expressed with an [Effect](/en/docs/learn/effects), not an `Either`.

## Try absence and failure separately

Change `ports` to an empty Array, `let ports: Array<Int> = []`: it prints `Port: 3000`. Change it to `[-1]`: there is a value, but it fails the check, so it prints `Invalid port: -1`. "No value" and "an invalid value" are handled separately.
