Building a string and printing it on the screen are two different things. The first gives the same result every time; the second affects the world outside the program.

Seseragi represents interactions with the outside world, such as output, reading and writing state, and asynchronous work, as values called `Effect`s. An Effect is a value describing "work that does something when run"; creating one does not do anything yet. This chapter covers creating Effects, running them, and handling failures.

## Receive the value from a successful computation

Start with an Effect that does not touch the outside world and simply returns a value. Import `std/effect`:

{/* example: examples/learn/focused/effect-bind.ssrg#import */}
```seseragi title="Import declaration"
import * as effects from "std/effect"
```

`succeed` turns an ordinary value into "an Effect that succeeds with that value":

{/* example: examples/learn/focused/effect-bind.ssrg#declaration */}
```seseragi title="Function declaration"
effect fn answer -> Int =
  effects.succeed 42
```

Calling `answer ()` returns not an integer but "an Effect that succeeds with 42". To use the value inside, take it out with `<-` in the `do` block of `main`:

{/* example: examples/learn/focused/effect-bind.ssrg#bind */}
```seseragi title="Expressions in main do"
value <- answer ()
value
|> show
|> println
```

This prints 42. `value <- answer ()` runs the Effect and receives its success value, which is an ordinary integer from then on. It is close to TypeScript's `const value = await answer()`.

## Creating an Effect does not run it

{/* example: examples/learn/effects.ssrg */}
```seseragi title="effects.ssrg"
effect fn greet name: String -> Unit
with Console
fails ConsoleError =
  println `Hello, ${name}`

pub effect fn main = do {
  let greeting = greet "Aki"
  println "Before greeting"
  greeting
  greeting
}
```

```text title="Output"
Before greeting
Hello, Aki
Hello, Aki
```

`let greeting = greet "Aki"` only creates "an Effect that prints a greeting" and names it; nothing is printed at that point. So `Before greeting` comes first. Running `greeting` twice afterward prints the greeting twice.

This is the big difference from a TypeScript Promise. A Promise starts working the moment it is created, and its result is produced only once. An Effect does not start when created, and does its work every time it runs. That is why an Effect can be treated as a plain value: stored in a variable, passed to a function, and run later as many times as you like.

## What an Effect's type tells you

The type `Effect<R, E, A>` carries three pieces of information: `R` is what the work needs, `E` is how it can fail, and `A` is the result on success. The type of `greet` is shown below; read it as "uses the console, may fail with `ConsoleError`, and returns `Unit` on success".

```seseragi
Effect<
  { console: Console },
  ConsoleError,
  Unit
>
```

In an `effect fn` declaration, `-> Unit` is the success type, `with Console` is what it needs, and `fails ConsoleError` is the failure type. The signature alone tells you what a function uses and how it can fail. A TypeScript function's type does not tell you whether it calls `fetch` or `console.log` inside, or what it might `throw`.

## Run in order with do

Effects written inside `do` run from top to bottom. To use a success value, write `value <- effect`. A `let` inside `do` just names an ordinary value and does not run an Effect.

The last line of a `do` must be an Effect. To return an ordinary value, wrap it with `succeed value` or `pure value`. Putting Effects in an ordinary block `{ ... }` without `do` does not run them in order.

You used `do` in [Maybe and Either](/en/docs/learn/maybe-and-either) too. The same notation means "stop if there is no value" for Maybe, "stop on failure" for Either, and "run the work in order, stopping on failure" for Effect.

## Write the types, or let them be inferred

`greet` writes out the success type, what it needs, and the failure type. When you omit all of `->`, `with`, and `fails`, as `main` does, everything is inferred from the body.

Be careful when you write the success type, as in `-> Unit`. Then an omitted `with` means "needs nothing" and an omitted `fails` means "cannot fail" (`Never`); they are not inferred from the body. To print to the console, also write `with Console` and `fails ConsoleError`, as in the example.

Even when inferred, what a function needs and how it fails remain part of its type. Requirements are merged automatically, but different failure types are never merged into one automatically. Decide how to classify failures yourself, with an ADT and `mapError`.

## Handle failures

Effects combined in one `do` must share the same failure type (`Never`, which cannot fail, fits any failure type). Express a possible failure with `fail`, and recover from it with `recover`.

### Recover from a failure

First define the failure type. This example also imports `std/effect` as `effects`:

{/* example: examples/learn/focused/effect-recovery.ssrg#failure-type */}
```seseragi title="Type declaration"
type CheckError =
  | Rejected
```

This Effect succeeds with 42 when `allowed` is `True`, and fails with `Rejected` when it is `False`:

{/* example: examples/learn/focused/effect-recovery.ssrg#declaration */}
```seseragi title="Function declaration"
effect fn accepted allowed: Bool
  -> Int fails CheckError =
  if allowed then
    effects.succeed 42
  else
    effects.fail Rejected
```

Prepare a function to run instead on failure. It returns an Effect with the same `Int` as the success case:

{/* example: examples/learn/focused/effect-recovery.ssrg#fallback */}
```seseragi title="Function declaration"
effect fn fallback error: CheckError
  -> Int =
  effects.succeed 0
```

Connect them with `recover`:

{/* example: examples/learn/focused/effect-recovery.ssrg#recover */}
```seseragi title="Expressions in main do"
value <-
  accepted False
  |> effects.recover fallback
```

`value` is 0. Change `False` to `True` and it becomes 42, without calling `fallback`. The function passed to `recover` runs only on failure. It resembles TypeScript's `try ... catch`, except that the type decides which failures can arrive.

### Convert the failure type

To turn a string failure into your application's ADT failure, use `mapError`. First, define the target type:

{/* example: examples/learn/focused/effect-map-error.ssrg#failure-type */}
```seseragi title="Type declaration"
type InputError =
  | Invalid String
```

The source is an Effect that fails with a string:

{/* example: examples/learn/focused/effect-map-error.ssrg#source */}
```seseragi title="Function declaration"
effect fn load -> String
fails String =
  effects.fail "empty"
```

`mapError Invalid` wraps the failure string in `Invalid`, making it an `InputError`:

{/* example: examples/learn/focused/effect-map-error.ssrg#mapping */}
```seseragi title="Function declaration"
effect fn checked -> String
fails InputError =
  load ()
  |> effects.mapError Invalid
```

`mapError` only changes the failure type; it does not recover. To recover, add `recover`:

{/* example: examples/learn/focused/effect-map-error.ssrg#recovery */}
```seseragi title="Recovery function"
effect fn describe error: InputError
  -> String =
  match error {
    Invalid reason -> {
      let message =
        `invalid: ${reason}`
      effects.succeed message
    }
  }
```

Use it in `main` like this:

{/* example: examples/learn/focused/effect-map-error.ssrg#use */}
```seseragi title="Expressions in main do"
value <-
  checked ()
  |> effects.recover describe
println value
```

This prints `invalid: empty`. `mapError` reclassifies a failure, and `recover` turns a failure into a success.

Crashes caused by bugs and cancelled work are separate from the failures expressed with `fails`. `recover` is not a `catch` that captures every abnormal outcome. The [Error handling](/en/docs/guides/error-handling) guide covers how to design failures.

When you run a program, the CLI runs the Effect returned by the `pub` `main`. `effect fn` is a readable way to write "a function that returns an Effect"; an ordinary `fn` can return an Effect too if you write its type.

## Change the execution count

Remove one of the lines that run `greeting`, and the greeting prints once. Keep only `let greeting = ...` and remove both, and no greeting prints. This confirms that creating an Effect does not run it.
