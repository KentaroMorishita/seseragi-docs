---
title: Write tests
description: Verify a public API with std/test and preserve meaningful boundary cases.
---

Test a function that returns a shipping fee of 0 for a subtotal of 3000 or more and 400 otherwise. Testing just below the boundary, exactly at it, and just above it means you notice right away if the condition is ever written wrong.

## Create a package for tests

Create the following files in `shipping/`. Functions go in `src/` and tests in `tests/`.

```text
shipping/
  seseragi.toml
  src/
    shipping.ssrg
  tests/
    shipping.ssrg
```

```toml title="seseragi.toml"
[package]
name = "docs/shipping"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "shipping"

[test]
target = "node"
jobs = 1
```

`"." = "shipping"` under `[exports]` publishes the `shipping` module as the package's entry. `target = "node"` under `[test]` sets where tests run, separately from the `target` under `[run]` for running an app.

## Write the public function

{/* example: examples/guides/testing/src/shipping.ssrg */}
```seseragi title="src/shipping.ssrg"
pub fn fee subtotal: Int -> Int =
  if subtotal >= 3000 then 0 else 400
```

Tests import `fee` the same way code outside the package would, so both `pub` on the function and the module's entry in `[exports]` are needed.

## Create a test tree

{/* example: examples/guides/testing/tests/shipping.ssrg */}
```seseragi title="tests/shipping.ssrg"
import * as test from "std/test"
import { fee } from "docs/shipping"

pub let tests: test.Test =
  test.suite "fee" [
    test.test "below threshold"
      (test.equal 400 (fee 2999)),
    test.test "at threshold"
      (test.equal 0 (fee 3000)),
    test.test "above threshold"
      (test.equal 0 (fee 3001))
  ]
```

`test.equal` takes the expected value first, then the actual value. The test runner looks for a value named `pub let tests: test.Test` and runs it.

`test.suite` and `test.test` only build an ordinary value describing the tests. A test's body runs only when the runner runs that test.

## Run the tests

Run the following in `shipping/`:

```sh
seseragi lock update
seseragi test
```

```text
PASS shipping::fee::below threshold
PASS shipping::fee::at threshold
PASS shipping::fee::above threshold
3 passed; 0 failed; 0 skipped
```

Try changing the condition to `subtotal > 3000`. After saving, run `seseragi lock update`, then `seseragi test`. `at threshold` fails, with 2 passed and 1 failed. Then change it back to `>=`, update the lockfile again, and rerun the tests.

Changing the source makes it disagree with the lockfile, so without updating it the run stops with `SES-K0102`. The exit code is 1 for failed tests, and 2 for problems such as a stale lockfile or a compile error.

## Run a subset

```sh
seseragi test --filter threshold
seseragi test --exact \
  shipping::fee::at\ threshold
```

`--filter` takes text contained in a test's name (case-sensitive, not a regular expression). `--exact` takes a test's full name. Either way, if no test matches, the run exits with code 2.

`--jobs` sets how many tests run at once. Results are still reported in the order the tests are defined.

## Test success and typed failure separately

Next, tests that check for failure. In a separate package, test the rule from [Forms](/en/docs/guides/forms), "strip surrounding spaces and reject the name if nothing is left", with four inputs.

### Prepare the names package

```sh
mkdir -p names/src names/tests
cd names
```

`seseragi.toml` is:

{/* example: examples/guides/testing-validation/seseragi.toml */}
```toml title="seseragi.toml"
[package]
name = "docs/names"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "names"

[test]
target = "node"
jobs = 1
```

Write the validation function in `src/names.ssrg`.

{/* example: examples/guides/testing-validation/src/names.ssrg#validator */}
```seseragi title="src/names.ssrg"
import * as text from "std/text"

alias Name = Either<String, String>

pub fn name input: String -> Name = {
  let cleaned = text.trim input
  if cleaned == "" then
    Left "missing name"
  else
    Right cleaned
}
```

### Specify expected values and failure reasons

Write these two blocks in order in `tests/names.ssrg`. `accepted` builds the expected success value, and `missing` checks whether a failure has the expected reason.

{/* example: examples/guides/testing-validation/tests/names.ssrg#helpers */}
```seseragi title="tests/names.ssrg"
import * as test from "std/test"
import * as effects from "std/effect"
import { name } from "docs/names"

alias Name = Either<String, String>

fn accepted value: String -> Name =
  Right value

fn missing error: String -> Bool =
  error == "missing name"
```

Valid input uses `test.equal`. Empty input uses `test.expectFailure`, which checks both that it fails and why.

{/* example: examples/guides/testing-validation/tests/names.ssrg#cases */}
```seseragi title="tests/names.ssrg"
pub let tests: test.Test =
  test.suite "name" [
    test.test "valid" $
      test.equal (accepted "Ada") $
        name "Ada",
    test.test "trimmed" $
      test.equal (accepted "Ada") $
        name " Ada ",
    test.test "blank" $
      name ""
      |> effects.fromEither
      |> test.expectFailure missing,
    test.test "spaces" $
      name "   "
      |> effects.fromEither
      |> test.expectFailure missing
  ]
```

```sh
seseragi lock update
seseragi test
```

```text
PASS names::name::valid
PASS names::name::trimmed
PASS names::name::blank
PASS names::name::spaces
4 passed; 0 failed; 0 skipped
```

`blank` and `spaces` pass because validation correctly fails. The validation result, an `Either`, is turned into an Effect with `effects.fromEither` before being passed in.

### Read failing tests

Change the expected value in `valid` to `accepted "Eve"`, update the lockfile, and run `seseragi test --filter valid`. The report shows that the expected `Right "Eve"` differs from the actual `Right "Ada"`. Change it back, then try the next two changes one at a time.

| Change | Problem reported by `blank` |
| --- | --- |
| Return `Right "default"` for empty input | `expected a typed failure` |
| Make `missing` require another reason | `typed failure did not match` |

For each, update the lockfile and run `seseragi test --filter blank`. The first is "expected to fail but succeeded", the second "failed for a different reason"; both make the test fail with exit code 1. After reverting, update the lockfile and check that all four pass.

`expectFailure` catches only failures expressed in types. It never treats a defect caused by a bug, or cancellation, as the expected failure.

## Choose what to verify

These tests check how functions behave, not how the screen behaves. Check input fields and clicks in a browser. A function like a view's `update`, though, can be tested directly with the same `test.equal` ([State and Actions](/en/docs/guides/state-and-actions)). Details on the runner's timeouts, filters, and exit codes are in the [CLI reference](/en/docs/reference/cli).
