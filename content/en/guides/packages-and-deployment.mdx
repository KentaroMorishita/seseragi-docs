---
title: Packages and deployment
description: Separate public APIs from entry points and distribute process or Web artifacts.
---

Pull a shipping calculation out into a small library and use it from another app. Which modules to publish and which packages to depend on are decided in `seseragi.toml`. The second half covers distributing CLI apps and Web apps.

It uses what you learned in [Modules](/en/docs/learn/modules) and [Local development](/en/docs/learn/local-development).

## Create two packages

Create the following files. `shipping/` is the library, and `app/` is the app that uses it:

```text
shop/
  shipping/
    seseragi.toml
    src/
      shipping.ssrg
  app/
    seseragi.toml
    src/
      main.ssrg
```

No shared configuration file is needed in the parent directory. Each directory with a `seseragi.toml` is one package.

## Define the library entry

```toml title="shipping/seseragi.toml"
[package]
name = "docs/shipping"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[exports]
"." = "shipping"
```

{/* example: examples/guides/packages/shipping/src/shipping.ssrg */}
```seseragi title="shipping/src/shipping.ssrg"
pub fn fee subtotal: Int -> Int =
  if subtotal >= 3000 then 0 else 400
```

`pub` exports the function, and `[exports]` decides which modules other packages can use. A module not listed in `[exports]` cannot be imported from another package, even by path: the same idea as `exports` in an npm `package.json`.

## Use a path dependency

```toml title="app/seseragi.toml"
[package]
name = "docs/shop"
version = "0.1.0"
language = ">=0.1.0 <0.2.0"

[run]
entry = "main"
target = "process"

[dependencies.shipping]
package = "docs/shipping"
path = "../shipping"
```

{/* example: examples/guides/packages/app/src/main.ssrg */}
```seseragi title="app/src/main.ssrg"
import { fee } from "shipping"

pub effect fn main =
  fee 2999
  |> show
  |> println
```

`shipping` is the name used in imports in the source. The real package name `docs/shipping` and the relative path to it, `../shipping`, are written out. Imports never point directly into another package's `src/`.

## Lock and run

Run the following in `shop/`:

```sh
seseragi lock update app
seseragi run app
```

```text
400
```

`app/seseragi.lock` records the contents of dependency packages and information about the tools used. After changing `seseragi.toml` or a dependency's source, check the changes and update the lockfile.

`run` and `build` never update the lockfile automatically; a stale one stops them with `SES-K0102`. Keep both `seseragi.toml` and `seseragi.lock` in version control.

## Run a process artifact

```sh
cd app
seseragi build . --profile release
bun dist/entry.js
```

The built program prints 400 too. Building bundles the generated JavaScript and the runtime into a single `entry.js`, which you run with Bun. It does not produce a standalone executable for your OS.

Apps such as HTTP servers are distributed the same way as this CLI app, not as a static site. [Runtime Providers](/en/docs/reference/runtime-providers) lists the features an app can use.

## Serve a Web artifact

Build the `counter/` project from [Build a Web application](/en/docs/guides/web-app):

```sh
seseragi lock update
seseragi build . --profile release
```

`dist/` contains `index.html` and the browser JavaScript and CSS. Put that directory on any static host and it is published. Showing the published page does not need Seseragi.

For example, with the Vercel CLI installed and logged in, publish the built directory:

```sh
vercel deploy dist --prod
```

Configure Vercel not to run an additional build. `--prod` publishes to the production domain. See the [official Vercel CLI documentation](https://vercel.com/docs/cli/deploy) for details.

## Add HTML and public files

To set your own page title or favicon, point `index` and `public` under `[web]` at your HTML file and static files directory. Put one `<!-- seseragi:head -->` in the HTML `head` and one `<!-- seseragi:entry -->` in the `body`, and include `<div id="app"></div>` where the view goes.

When you add or change static files, update the lockfile before building as well. Never edit the generated `dist/` by hand. The detailed rules are in [Project configuration](/en/docs/reference/project-configuration).

## Check the publication boundary

Path dependencies support local development. They cannot remain in a manifest published to a registry. The current CLI has no package `publish` command; this guide covers local package separation and distribution of application artifacts.

After changing which modules are published, [Testing](/en/docs/guides/testing) lets you check that imports from outside still work. To publish TypeScript bindings, publish the handwritten wrapper introduced in [TypeScript bindings](/en/docs/guides/typescript-bindings).
