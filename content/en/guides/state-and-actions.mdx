title: State and Actions
description: Keep update rules pure so you can verify them independently of views and effects.
---

Check the “increment” and “reset” of the counter from [Build a Web application](/en/docs/guides/web-app) without a screen. Gathering “how each operation changes the state” into one function, `update`, lets you verify behavior before building the screen.

## Separate state from an operation

The state is an `Int` holding the current count, and operations are an `Action` with two cases, `Increment` and `Reset`. `update action state` returns the new state from an operation and the current state.

Keep operations and state as separate types. The state after a `Reset` is `0`, not `Reset`.

## Save the complete update example

Save the following as `state.ssrg`.

{/* example: examples/guides/state.ssrg */}
```seseragi title="state.ssrg"
type Action =
  | Increment
  | Reset

fn update action: Action -> n: Int
  -> Int =
  match action {
    Increment -> n + 1
    Reset -> 0
  }

pub effect fn main = do {
  0
  |> update Increment
  |> update Increment
  |> show
  |> println
  5
  |> update Reset
  |> show
  |> println
}
```

`update Increment` is a function waiting for a state (partial application). So `0 |> update Increment` means the same as `update Increment 0`, and you can chain operations in a pipeline.

## Execute a sequence of operations

```sh
seseragi run state.ssrg
```

```text
2
0
```

The first pipeline applies `Increment` to 0 twice, giving 2; the second applies `Reset` to 5, giving 0. Apart from `println`, everything just computes values, so the result is the same every time.

## Group several values into state

In a form, you often want the state to hold the text being typed and a message as well as a number. Group them into a struct. To update it, create a new value such as `Model { ...model, draft: value }`; fields cannot be assigned. [Forms](/en/docs/guides/forms) has a larger example.

### Change one field at a time

This example holds a count and the text being typed. Write the following three blocks in order in `state-fields.ssrg`.

{/* example: examples/guides/state-fields.ssrg#model */}
```seseragi title="state-fields.ssrg"
struct Model {
  count: Int,
  draft: String
}

type Action =
  | Edited String
  | ResetCount
```

`Edited` carries the typed text, and `ResetCount` sets only the count to 0. Fields that do not change are carried over with `...model`.

{/* example: examples/guides/state-fields.ssrg#update */}
```seseragi title="state-fields.ssrg"
fn update action: Action
  -> model: Model -> Model =
  match action {
    Edited draft -> Model {
      ...model,
      draft
    }
    ResetCount -> Model {
      ...model,
      count: 0
    }
  }
```

### Compare original and updated values

{/* example: examples/guides/state-fields.ssrg#cases */}
```seseragi title="state-fields.ssrg"
pub effect fn main = do {
  let initial = Model {
    count: 2,
    draft: ""
  }
  let edited =
    update (Edited "Ada") initial
  println edited.draft
  println `Count: ${edited.count}`
  `Original: "${initial.draft}"`
  |> println
  let reset =
    update ResetCount edited
  println `Count: ${reset.count}`
  println reset.draft
}
```

```sh
seseragi run state-fields.ssrg
```

```text
Ada
Count: 2
Original: ""
Count: 0
Ada
```

After editing, `draft` is `Ada`, while the original `initial.draft` stays empty. `Edited` keeps the count of 2, and `ResetCount` keeps the text `Ada`.

## Place effects at an execution boundary

`update` only computes values, so it cannot do things like network requests.

When you need such work, separate the part that runs Effects from the part that updates state. [Stateful features](/en/docs/guides/stateful-features) shows updating a Signal directly. If you send the result of a request back to `update` as an Action, give the Action cases for both success and failure.

## Test the update rules

Instead of clicking buttons every time, write tests such as “`update Increment 0` is 1” and “`update Reset 5` is 0”. [Testing](/en/docs/guides/testing) shows how.

When you add a case to Action, the compiler also checks that the `match` in `update` handles it. The detailed rules for patterns are in the [patterns reference](/en/docs/reference/patterns).
