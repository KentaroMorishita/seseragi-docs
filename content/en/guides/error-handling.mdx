---
title: Handle failures
description: Distinguish pure validation from Effect failure and turn input problems into useful messages.
---

Build a program that validates a quantity and shows either the quantity or how to fix the input. Text that is not a number and a number out of range are treated as different failures.

It combines what you learned in [Maybe and Either](/en/docs/learn/maybe-and-either) and [Effects](/en/docs/learn/effects).

## Represent failure with a type

The kinds of failure become a type, `QuantityError`, with two cases: `NotANumber` and `OutsideRange`. The `quantity` function returns `Either<QuantityError, Int>`: the quantity on success, the reason on failure.

If having no value is an ordinary result, `Maybe` is fine. Here the user needs a reason to fix the input, so it uses `Either`.

## Save the complete program

Save the following as `errors.ssrg`.

{/* example: examples/guides/errors.ssrg */}
```seseragi title="errors.ssrg"
import * as ints from "std/int"
import * as effects from "std/effect"

type QuantityError deriving Show =
  | NotANumber
  | OutsideRange

alias Result =
  Either<QuantityError, Int>

fn quantity text: String -> Result =
  match ints.parse text {
    Left _ -> Left NotANumber
    Right n ->
      if n >= 1 && n <= 1000 then
        Right n
      else
        Left OutsideRange
  }

effect fn report text: String = do {
  result <-
    quantity text
    |> fromEither
    |> effects.attempt
  let message = match result {
    Right n -> `Quantity: ${n}`
    Left NotANumber ->
      "Enter a number"
    Left OutsideRange ->
      "Use 1 to 1000"
  }
  println message
}

pub effect fn main = do {
  report "3"
  report "many"
  report "0"
}
```

The detailed failure from `ints.parse` is collapsed into `NotANumber` here. The range rule lives in `quantity` and the wording lives in the `match` in `report`, so it is clear where to look for what.

## Move an Either into an Effect

`fromEither` creates an Effect that succeeds for `Right` and fails for `Left`. `effects.attempt` goes the other way: it catches the Effect's failure and returns `Right` on success or `Left` on failure, as a value.

Thanks to `attempt`, `report` can handle success and failure as ordinary values with `match`, and build text to display in either case.

## Inspect the result

```sh
seseragi run errors.ssrg
```

```text
Quantity: 3
Enter a number
Use 1 to 1000
```

The failures for “many” and 0 are turned into messages, so the program as a whole succeeds. It does not handle a failure of `println` itself, though; such a failure is not turned into success.

## Use a default only on failure

The next, separate example uses `light` when there is no theme setting, and the setting otherwise. Write the following two blocks in order in `error-recovery.ssrg`. It reads no files; whether a setting exists is passed as a `Maybe<String>`.

{/* example: examples/guides/error-recovery.ssrg#fallback */}
```seseragi title="error-recovery.ssrg"
import * as effects from "std/effect"

type ThemeError =
  | MissingSetting

effect fn theme saved: Maybe<String>
  -> String fails ThemeError =
  effects.fromMaybe MissingSetting $
    saved

effect fn fallback error: ThemeError
  -> String =
  match error {
    MissingSetting -> succeed "light"
  }
```

`effects.fromMaybe` creates an Effect that fails with `MissingSetting` for `Nothing`. `fallback` is an Effect that returns `light` instead on failure. It needs nothing and cannot fail, so its type is `Task<String>`.

{/* example: examples/guides/error-recovery.ssrg#paths */}
```seseragi title="error-recovery.ssrg"
pub effect fn main = do {
  missing <-
    theme Nothing
    |> effects.recover fallback
  println missing
  present <-
    theme (Just "dark")
    |> effects.recover fallback
  println present
}
```

```sh
seseragi run error-recovery.ssrg
```

```text
light
dark
```

Passing `Nothing` fails, so `recover` calls `fallback` and the result is `light`. `Just "dark"` succeeds, so the result is `dark` as is.

`attempt` in the previous example receives success and failure as values to inspect; `recover` in this example runs a replacement Effect on failure.

## Unify application failures

When you combine Effects with different failure types, such as input, files, and network, bring them to the application's failure type with `mapError`. [Build a CLI application](/en/docs/guides/cli-app) merges `InputFailure StdinError` and `OutputFailure ConsoleError` into one `AppError`.

`map` transforms success values; `mapError` transforms failure reasons. Whether to recover and continue or return the failure to the caller is a decision for each application.

## Bugs and cancellation are separate

`attempt` and `recover` handle only the failures written in types with `fails`. Abnormal outcomes caused by bugs (defects) and cancelled work cannot be caught as ordinary failures.

Seseragi has no `try/catch` syntax. To handle exceptions thrown by TypeScript functions, use a `task` binding, introduced in [TypeScript bindings](/en/docs/guides/typescript-bindings). The detailed rules for failures, defects, and cancellation are in the [Effect reference](/en/docs/reference/effects).
