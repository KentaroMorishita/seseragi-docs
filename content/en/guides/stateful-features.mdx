---
title: Compose stateful features
description: Create a private Signal and return a read-only view to the parent.
---

Place two counters, “Today” and “Tomorrow”, side by side so that pressing one leaves the other unchanged. The counter module owns its state and returns only its view (`Signal<Html<Task<Unit>>>`) to the parent. The parent never touches the child's state.

It uses what you learned in [Effects](/en/docs/learn/effects), [Signals](/en/docs/learn/signals), and [Modules](/en/docs/learn/modules). State uses a [struct](/en/docs/learn/records-and-structs), button handlers use lambdas from [Functions](/en/docs/learn/functions), and `$` from [The application operator](/en/docs/learn/application-operator) removes parentheses. `Task<Unit>` is an alias for `Effect<{}, Never, Unit>`, an Effect that needs nothing and cannot fail. A button carries such a Task as its Action for clicks.

## Prepare a project

```sh
seseragi new web two-counters
cd two-counters
```

In a project created with `seseragi new web`, add `src/counter.ssrg` and replace `src/main.ssrg`. The generated `app.ssrg` is not used.

## Let the child create its state

{/* example: examples/guides/stateful-features/src/counter.ssrg */}
```seseragi title="src/counter.ssrg"
import * as html from "std/web/html"
import * as signals from "std/signal"
import { MutableSignal, Signal }
  from "std/signal"

struct Count { count: Int }

alias View = html.Html<Task<Unit>>

fn view title: String
  -> state: MutableSignal<Count>
  -> current: Count
  -> View =
  html.section {
    children: [
      html.h2<Task<Unit>, String> {
        children: title
      },
      html.p<Task<Unit>, String> {
        children: show current.count
      },
      html.button {
        buttonType: "button",
        children: "Add one",
        onClick: signals.update
          (\n: Count -> Count {
            count: n.count + 1
          }) state
      }
    ]
  }

pub effect fn create title: String
  -> Signal<View> = do {
  state <-
    signals.make $ Count { count: 0 }
  state
  |> signals.map (view title state)
  |> succeed
}
```

`create` is an Effect: running it creates one piece of state with `signals.make` and returns a Signal of the view built from that state.

The writable `MutableSignal` stays inside the module; the parent gets only a read-only `Signal`. Each button carries "a Task that updates the state" as its Action, so the parent does not need to know what Actions the child has.

## Compose views in the parent

{/* example: examples/guides/stateful-features/src/main.ssrg */}
```seseragi title="src/main.ssrg"
import * as dom from "std/web/dom"
import * as html from "std/web/html"
import * as signals from "std/signal"
import { create } from "./counter"

alias View = html.Html<Task<Unit>>

fn layout first: View -> second: View
  -> View =
  html.main {
    style: html.style {
      margin: "32px auto",
      maxWidth: "32rem",
      padding: "24px"
    },
    children: [first, second]
  }

fn perform action: Task<Unit>
  -> Task<Unit> = action

fn queryError error: dom.DomError
  -> String = show error

alias DomFailure =
  dom.DomRuntimeError<Never>

fn runtimeError error: DomFailure
  -> String = show error

pub effect fn main = do {
  first <- create "Today"
  second <- create "Tomorrow"
  let content =
    signals.combine layout first $
      second
  target <-
    dom.query "#app"
    |> mapError queryError
  let options = dom.defaultOptions ()
  (
    dom.run options target perform $
      content
  )
  |> mapError runtimeError
}
```

`create "Today"` and `create "Tomorrow"` each run and create separate state. `signals.combine` passes the two views to `layout`, combining them into one view.

`perform` just returns the Task the child prepared. On a click, `dom.run` runs that Task.

## Verify independence in a browser

```sh
seseragi lock update
seseragi dev --open
```

Both start at 0. Click “Add one” under “Today” twice and only Today becomes 2; click “Tomorrow” once and Tomorrow becomes 1, while Today stays 2.

How many pieces of state exist depends on how many times `create` runs. Redrawing the screen never recreates state, and an HTML `key` does not decide it either.

## Check Signal creation in isolation

These two programs check that state is independent, without a screen. Save each in its own file.

### Execute make separately

`signal-independence.ssrg` runs `signals.make` twice. Updating one does not change the other.

{/* example: examples/guides/signal-independence.ssrg#independent */}
```seseragi title="signal-independence.ssrg"
import * as signals from "std/signal"

fn increment n: Int -> Int = n + 1

pub effect fn main = do {
  first <- signals.make 0
  second <- signals.make 0
  signals.update increment first
  signals.update increment first
  signals.update increment second
  today <- signals.read first
  tomorrow <- signals.read second
  println `Today: ${today}`
  println `Tomorrow: ${tomorrow}`
}
```

```sh
seseragi run signal-independence.ssrg
```

```text
Today: 2
Tomorrow: 1
```

`signals.read` reads the value at that moment.

### Bind another name to the same Signal

`signal-shared.ssrg` runs `make` only once. `same` points to the same Signal as `source`.

{/* example: examples/guides/signal-shared.ssrg#shared */}
```seseragi title="signal-shared.ssrg"
import * as signals from "std/signal"

pub effect fn main = do {
  source <- signals.make 0
  let same = source
  signals.set 2 same
  first <- signals.read source
  second <- signals.read same
  println `Source: ${first}`
  println `Same: ${second}`
}
```

```sh
seseragi run signal-shared.ssrg
```

```text
Source: 2
Same: 2
```

`let same = source` only adds a name; it does not copy the state. For separate state, run `make` for each; to share state, pass the same Signal.

## Choose the owner of shared state

If two counters should work on the same value, their common parent creates the state and passes the children only the current value and the update Tasks it allows. Passing a child the application's whole `MutableSignal` would let it change anything.

Create application-wide state in the topmost parent. Do not put global state at the top level of a module.

## Distinguish shutdown from resource ownership

`dom.run` manages the subscriptions and event listeners it uses to update the screen, and releases them when it ends. Its own failures are converted to `String` with `mapError`.

If a child owns subscriptions, timers, or connections of its own, tie their cleanup to an Effect scope or a `DomMount`. Disappearing from the screen does not clean them up automatically. The detailed rules are in the [Signal reference](/en/docs/reference/signals) and the [Web UI reference](/en/docs/reference/web-ui).
